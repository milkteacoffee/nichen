# 素材替换说明（换皮指南）

《逆尘》的画面分两层：

1. **素材层**（本目录）：`assets/manifest.json` 里登记"逻辑名 → 图片路径"。
2. **程序化层**（`js/core/art.js`、`js/core/sprites.js`）：没有素材时实时绘制的兜底画面。

**绘制规则：先查素材层，命中用你的图，未命中才程序化画。** 所以你可以只替换一部分素材，
其余部分照常显示，不会裂图、不会报错。

> **当前状态：素材层已装了一批 AI 生成的角色形象**（主角地图行走图四向 + 战斗立绘 7 张），
> 见 `_gen/`（生成原图）与 `assets/img/`（切好的成品）。其余部分仍是程序化画面。

### manifest 有两个副本，改哪个？

`assets-build.py` 同时产出两样东西，内容一致：

| 文件 | 加载方式 | 说明 |
|---|---|---|
| `assets/manifest.js` | `<script>` 标签引入，挂到 `G.AssetManifest` | **引擎优先读它** |
| `assets/manifest.json` | `fetch()` | 仅作为 JS 缺失时的退路 |

**为什么优先 JS**：`manifest.json` 只能靠 fetch 取，而 fetch 在 `file://` 下打开、
以及部分沙箱预览里会被拦 —— 一被拦就**静默退回全程序化画面**，玩家只会觉得
"人物怎么跟我放进去的图不一样"，完全看不出是素材没加载。`<script>` 标签没这个问题。

所以：**改完图一律重跑 `python tools/assets-build.py`**，让它两个文件一起更新；
手工改 `manifest.json` 是没用的（除非把 `manifest.js` 也改了）。

## 一、怎么替换

1. 把图片放进 `www/assets/img/`（PNG 透明底，或 WebP）。
2. 在 `www/assets/manifest.json` 里登记（然后重跑 `assets-build.py` 同步到 `.js`），例如：

```json
{
  "tile.grass.0": "assets/img/tile_grass_0.png",
  "tile.grass.1": "assets/img/tile_grass_1.png",
  "char.hero.down.0": "assets/img/hero_down_0.png",
  "bg.title": "assets/img/title_bg.webp"
}
```

3. 重新打开游戏即可生效（浏览器会缓存，强刷 Ctrl+F5）。

> 没有登记的键 = 继续用程序化画面。可以一点点替换，随时可回退（删掉那行即可）。

### 用 AI 生图换角色（推荐流程）

生图工具出的是 1024×1024 方图，角色四周留大片透明边距、各角色占比还不一致。
**直接登记方图会让角色在槽位里偏小偏一侧，而且同一战场上大小不一。**
所以统一走一道切图：

```bash
# 1) 生成原图，命名成逻辑名放进 _gen/（如 battle.hero.png、char.hero.down.png）
# 2) 切图：裁到 alpha 外接框 → 按目标宽高比补透明边 → LANCZOS 缩放到目标尺寸 → 写 manifest
python tools/assets-build.py
# 3) 校验 manifest 与文件是否对得上、是否都有透明底
python tools/assets-build.py --check
```

`_gen/` 的文件名就是逻辑名。脚本会自动处理两件事：
- `char.hero.left` 会镜像出 `char.hero.right`（侧面图统一朝左画，右侧由镜像得到）；
- `char.hero.<dir>` 会展开成 `.0/.1/.2` 三个帧键（登记同一张图，走路动感由引擎里
  第 1 帧整体上抬 1 逻辑像素提供）。

  为什么必须有它：上面那些 node 工具用的是桩 canvas + 桩 fetch，**fetch 被桩成 reject，
  manifest 永远加载失败，素材路径在无头环境里根本跑不到**。只有真浏览器能回答
  "素材到底生效没有"。它会报：manifest 键数与来源、超采样 S 与美术 K 是否一致、

  并打印 ASCII 缩略图，用于确认角色没有被框裁切。需要本机 Chrome/Edge，
  且要先用 `python -m http.server 8173`（在 `www/` 下）起一个服务。
  另外三个模式：`perf`（冷启动/稳态/rAF 分场景测量）、`ablate`（消融定位瓶颈）、
  `ground`（地面渲染等价性逐像素比对）。

### 帧耗优化（三处，都验证过）

`bench-frame.js` 在 S=4 下的最小帧耗：**镇 1.5ms、野外 2.4ms、洞 1.5ms、室内 1.0—1.2ms**
（软件光栅器）。优化前是 7—15ms，提速 5—8 倍。
**单轮测量噪声极大（同一场景能差 2 倍），以多轮最小值为准。**

1. **地面预烘成整图层**（最大头，占优化前帧耗的 80%）。
   地面是**完全静态**的，只随地图与调色板变，相机怎么动都不影响像素内容 ——
   原先却每帧逐格从 672×672 的大纹理里取 16×16 子块，30×18=**540 次 blit**，
   实测每帧 7.8~22.6ms，室内大图直接掉到 30fps。
   现在整张地图烘成一张离屏层，每帧只 blit 视口那块（**1 次**）。
   - 烘焙内部也不逐格画：地面是周期纹理（TS=224=14×16 格），"按 TS 对齐平铺"
     与"逐格取 `(tx*16)%TS` 子块"逐像素等价，blit 次数从整图格数（field 2000 格）
     降到 6 次左右，只有路格与路缘才逐格补画。
   - **试过按周期分块，反而更慢 3~5 倍**：块是 224 逻辑（672 设备）而视口才 480×272，
     边界块只有部分可见，12 块合起来要搬 5.4M 像素；整图一次 blit 的传输量
     正好等于视口（1.18M），才是最优解。别再往分块方向改。
   - 画面正确性由 `browser-probe.js ground` 保证：老画法与新画法**逐像素完全一致**
     （5 张地图、1000 万+ 像素零差异）。
2. **室内环境光预烘**。`_drawIndoor` 原本每帧现算 2 个全屏径向渐变 + 2 次全屏 alpha
   填充（S=4 时是 2×2.09M 像素的逐像素渐变求值），四张室内图就是被它从 60fps
   压到 30fps 的。渐变几何是写死的，烘成一张整屏叠加层后每帧只 1 次 blit。
3. **装饰物缩放量化成 3 档预烘**。原来是 0.90~1.12 的连续随机缩放，每个装饰物
   每帧都过一次带滤波的缩放（野外一屏上百个）；而且非整数倍重采样会把像素画糊掉。
   现在量化成 `A.DECOR_SCALES = [0.92, 1.0, 1.08]` 预烘，绘制退化成 1:1 整数 blit。
   变体(3) × 档位(3) × 翻转(2) = 18 种组合，够打散复制感。

#### 量性能必须用对工具

- **逐阶段计时在 Chrome 上不可信**。Canvas2D 是**延迟渲染**的，`drawImage` 只是把命令
  塞进 display list，真正的光栅化发生在 flush 时 —— 给每个 `_draw*` 包一层计时，
  时间会被记到"恰好触发 flush 的那一步"头上。曾把地面层的开销全记到 `_drawDecor`，
  得出完全相反的结论。要看真实开销，用**消融**（`browser-probe.js ablate`：
  把某一步换成空函数，比较真实 rAF 帧间隔的差值）。
- **软件光栅器与浏览器差好几倍**（`bench-frame.js` 用 @napi-rs/canvas）。
  卡顿是玩家在浏览器里感受到的，最终要在浏览器里量。
- `WIN=1920,1080` 可让探针触发 S=4（1080p 全屏的 worst case，画布比 S=3 大 78%）。
  `GPU=1` 切到 GPU 加速档；默认 `--disable-gpu` 是刻意选的保守档（数值稳定、可跨机比较）。
