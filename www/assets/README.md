# 素材替换说明（换皮指南）

《逆尘》的画面分两层：

1. **素材层**（本目录）：`assets/manifest.json` 里登记"逻辑名 → 图片路径"。
2. **程序化层**（`js/core/art.js`、`js/core/sprites.js`）：没有素材时实时绘制的兜底画面。

**绘制规则：先查素材层，命中用你的图，未命中才程序化画。** 所以你可以只替换一部分素材，
其余部分照常显示，不会裂图、不会报错。

> **当前状态：素材层已装了一批 AI 生成的角色形象**（主角地图行走图四向 + 战斗立绘 7 张），
> 见 `_gen/`（生成原图）与 `assets/img/`（切好的成品）。其余部分仍是程序化画面。

### manifest 有两个副本，改哪个？

`assets-build.py` 同时产出两样东西，内容一致：

| 文件 | 加载方式 | 说明 |
|---|---|---|
| `assets/manifest.js` | `<script>` 标签引入，挂到 `G.AssetManifest` | **引擎优先读它** |
| `assets/manifest.json` | `fetch()` | 仅作为 JS 缺失时的退路 |

**为什么优先 JS**：`manifest.json` 只能靠 fetch 取，而 fetch 在 `file://` 下打开、
以及部分沙箱预览里会被拦 —— 一被拦就**静默退回全程序化画面**，玩家只会觉得
"人物怎么跟我放进去的图不一样"，完全看不出是素材没加载。`<script>` 标签没这个问题。

所以：**改完图一律重跑 `python tools/assets-build.py`**，让它两个文件一起更新；
手工改 `manifest.json` 是没用的（除非把 `manifest.js` 也改了）。

## 一、怎么替换

1. 把图片放进 `www/assets/img/`（PNG 透明底，或 WebP）。
2. 在 `www/assets/manifest.json` 里登记（然后重跑 `assets-build.py` 同步到 `.js`），例如：

```json
{
  "tile.grass.0": "assets/img/tile_grass_0.png",
  "tile.grass.1": "assets/img/tile_grass_1.png",
  "char.hero.down.0": "assets/img/hero_down_0.png",
  "bg.title": "assets/img/title_bg.webp"
}
```

3. 重新打开游戏即可生效（浏览器会缓存，强刷 Ctrl+F5）。

> 没有登记的键 = 继续用程序化画面。可以一点点替换，随时可回退（删掉那行即可）。

### 用 AI 生图换角色（推荐流程）

生图工具出的是 1024×1024 方图，角色四周留大片透明边距、各角色占比还不一致。
**直接登记方图会让角色在槽位里偏小偏一侧，而且同一战场上大小不一。**
所以统一走一道切图：

```bash
# 1) 生成原图，命名成逻辑名放进 _gen/（如 battle.hero.png、char.hero.down.png）
# 2) 切图：裁到 alpha 外接框 → 按目标宽高比补透明边 → LANCZOS 缩放到目标尺寸 → 写 manifest
python tools/assets-build.py
# 3) 校验 manifest 与文件是否对得上、是否都有透明底
python tools/assets-build.py --check
```

#### 画风必须"锚"在已有素材上（**重要，别只靠文字描述**）

实测同一段"Q版二头身、大像素颗粒、无粗黑描边"提示词，出图的比例、描边粗细、
像素粒度**都跟主角对不上**（把 NPC 做得比主角高一截、脸更细、还带一圈粗黑描边）。
改成**把主角素材当参考图喂进去**（image-to-image，参考 `www/assets/img/char.hero.down.png`，
风格保真度取中档），头身比 / 像素颗粒 / 描边处理立刻对齐。

提示词写法：

```
<角色名><用途>，严格沿用参考图的像素画风：相同的大像素颗粒大小、
相同的扁平上色与深色像素压结构（无粗黑描边）、相同的身高比例与头身比、
相同的低饱和仙侠配色。把角色换成：<外貌描述>。全身正面站姿，…
```

两条纪律：

- **地图精灵锚主角行走图**（`char.hero.down`）；**立绘锚主角战斗立绘**（`battle.hero`）
  —— 这两者本来就是两套画风，不要混用参考图。
- **已有战斗立绘的反派**（`killer` / `heartDemon`）出立绘时，参考图要用**它自己的战斗立绘**，
  否则对话立绘和战斗立绘会变成两个人（§5.5 记过这个坑）。

`_gen/` 的文件名就是逻辑名。脚本会自动处理两件事：
- `char.hero.left` 会镜像出 `char.hero.right`（侧面图统一朝左画，右侧由镜像得到）；
- `char.hero.<dir>` 会展开成 `.0/.1/.2` 三个帧键（登记同一张图，走路动感由引擎里
  第 1 帧整体上抬 1 逻辑像素提供）。

> **主角为什么要出两张**（v0.8.0 的教训）：原先角色面板直接复用 `battle.hero`（**战斗侧身站姿**），
> 玩家看到的是"侧脸背影"，反馈说"这个角色应该是正面图片"。
> 于是补 `portrait.luchen`（正面全身，角色面板用）。
> 但圆头像**不能**拿全身立绘裁头：圆里只要"脸"那一小块，全身立绘的脸在源图里约 9 逻辑 px 宽，
> 放到 36 逻辑 px 的圆里要放大 4 倍 → 糊成一团。所以**再出一张正面胸像** `avatar.luchen`，
> 面部像素密度够，裁出来才是清晰的正面脸。

> **为什么是 512 而不是 256**：立绘框逻辑尺寸 74×74，超采样上限 K=4 → 至少 296 才不被放大。
> 256 会在 K=4 时被拉大 1.16 倍、肉眼发虚；512 是干净的 1/2 下采样，最锐。
> （`tools/assets-build.py` 的 `SIZES` 已按 512 登记。）

> **一律走 `G.Art.portrait(key)`**，取值顺序是一条**三级兜底链**：
> 1. `portrait.<key>` 专属立绘（手绘/AI 出的半身像，最优先）；
> 2. `art.js` 的 `PORTRAIT_ART` 表 —— 主角与几个主要反派本来就有战斗立绘，
>    直接复用（`luchen→battle.hero`、`killer→battle.enemy.killer`、
>    `demon→battle.enemy.heartDemon`）。**没有这一级时角色面板会显示一张
>    跟地图上走着的人毫无关系的程序化半身像**（用户报过"面板和人物不一致"）；
> 3. 程序化半身像（`PORTRAIT_P` 参数表 + `portraitDraw`）。
>
> 素材那一支会先量出**不透明像素的包围盒**再按内容居中（`contentBox`）：
> AI 出图四周留白不对称（战斗立绘的刀往左伸、头发往右飘），按整图居中会让
> 可见内容整体偏出画框中心。裁完再乘 `PORTRAIT_FIT = 0.92` 留呼吸位，
> 否则头顶会贴到框上沿（只剩 0.7px）。
>
> 逻辑尺寸就是立绘框的 **74×74**，1:1 绘制 —— 所以素材会被烘进 74×74 的
> 逻辑画布（×K 超采样），不需要你自己缩到 74。出图建议 256×256 方图、透明底。
> 想换某个角色的长相，改 `PORTRAIT_P` 里的配色，或直接丢一张 `portrait.<key>.png`
> 进 `_gen/` 走切图流程。

#### 圆形头像的取景（`AVATAR_HEAD`）

主界面左上角的圆形头像是裁出来的，走 `G.UI.avatar(x, cx, cy, r, key)` → `A.avatar(key)`。
**优先用专用胸像**（`A.AVATAR_ART = { luchen: 'avatar.luchen' }`），没登记才回退到立绘。
它按 `A.headBox(key)` 给的 `[cx, cy, 源正方形边长]` 取一块正方形再裁圆。
**这个取景是一张显式表，不自动检测**：

```js
var AVATAR_ART = { luchen: 'avatar.luchen' };        /* 专用正面胸像，优先 */
var AVATAR_HEAD = {
  luchen: [36, 12, 20],          /* 兜底：portrait.luchen 全身正面立绘 */
  'avatar.luchen': [36, 34, 44]  /* 专用胸像：脸心略偏上、含肩 */
};
var AVATAR_HEAD_DEF = [37, 27, 44];                  /* 兜底 = 程序化半身像的几何 */
```

为什么不自动检测：实测 `battle.hero` 的逐行 alpha 宽度是
`y3:w3 → y10:w17 → y17:w11 → y24:w18 → y45:w25 → y56:w32`
—— 肩颈是**平滑过渡**，没有"脖子塌陷"这个断点，任何"宽度突变就停"的启发式都会一路扫到腰
（第一版就是这么写的，头像里只剩一件蓝袍子）。立绘有两种版式，取景本来就不该用同一条规则：

| 版式 | 头在框里的位置 | 取景 |
|---|---|---|
| 全身站姿（`battle.hero`） | 发髻 y=3、下巴 y=17，只占框高 20% | `[36, 12, 20]` |
| 半身像（程序化 `portraitDraw`） | 头心 y=27、头半径 16，占框高 43% | `[37, 27, 44]` |

**换立绘素材时这张表要一起改**，否则头像会裁到腰带或只剩半个头。
判断方法：跑 `node tools/shot.js 04_hud` 然后看 `_shots/04_hud.png` 左上角。

## 三、出图规格建议

| 项 | 建议 |
|---|---|
| 瓦片 | 48×48 PNG（等于 3× 逻辑像素，最锐利） |
| 地图角色（主角 / NPC） | 168×252 PNG（逻辑 28×42，比例 2:3 必须一致），脚底对齐画布下沿 |
| 战斗立绘 | 192×192 PNG（逻辑 40×40，正方形槽位，内部按原比例居中） |
| 人物立绘 | 512×512 方图 PNG（透明底，会被烘进 74×74 的逻辑立绘框；尺寸理由见 §8） |
| 立绘/背景 | 1920×1088 WebP（体积小） |
| 透明底 | 瓦片、角色、立绘必须透明底；背景不透明 |
| 色彩 | 与 `doc/《逆尘》美术音频与技术打包圣经 v0.2.md` §2.2 主题色板保持一致 |

> 超采样倍率现在是 3—4 自适应（见 `game.js` 的 `resize`）。素材尺寸只要 ≥ 逻辑尺寸×4
> 就不会被放大；低于这个值会在高倍率下变糊。`assets-build.py` 里的目标尺寸已经按 ×4 定好。

### 帧耗优化（四处，都验证过）

`bench-frame.js` 在 S=4 下的最小帧耗：**镇 1.9—2.1ms、野外 2.7—3.4ms、洞 1.7—2.6ms、
室内 1.3—2.5ms**（软件光栅器；优化前是 7—15ms，提速 5—8 倍）。
**单轮测量噪声极大（同一场景能差 2 倍），以多轮最小值为准。**

1. **地面预烘成整图层**（最大头，占优化前帧耗的 80%）。
   地面是**完全静态**的，只随地图与调色板变，相机怎么动都不影响像素内容 ——
   原先却每帧逐格从 672×672 的大纹理里取 16×16 子块，30×18=**540 次 blit**，
   实测每帧 7.8~22.6ms，室内大图直接掉到 30fps。
   现在整张地图烘成一张离屏层，每帧只 blit 视口那块（**1 次**）。
   - 烘焙内部也不逐格画：地面是周期纹理（TS=224=14×16 格），"按 TS 对齐平铺"
     与"逐格取 `(tx*16)%TS` 子块"逐像素等价，blit 次数从整图格数（field 2000 格）
     降到 6 次左右，只有路格与路缘才逐格补画。
   - **试过按周期分块，反而更慢 3~5 倍**：块是 224 逻辑（672 设备）而视口才 480×272，
     边界块只有部分可见，12 块合起来要搬 5.4M 像素；整图一次 blit 的传输量
     正好等于视口（1.18M），才是最优解。别再往分块方向改。
   - 画面正确性由 `browser-probe.js ground` 保证：老画法与新画法**逐像素完全一致**
     （5 张地图、1000 万+ 像素零差异）。
2. **室内环境光预烘**。`_drawIndoor` 原本每帧现算 2 个全屏径向渐变 + 2 次全屏 alpha
   填充（S=4 时是 2×2.09M 像素的逐像素渐变求值），四张室内图就是被它从 60fps
   压到 30fps 的。渐变几何是写死的，烘成一张整屏叠加层后每帧只 1 次 blit。
3. **装饰物缩放量化成 3 档预烘**。原来是 0.90~1.12 的连续随机缩放，每个装饰物
   每帧都过一次带滤波的缩放（野外一屏上百个）；而且非整数倍重采样会把像素画糊掉。
   现在量化成 `A.DECOR_SCALES = [0.92, 1.0, 1.08]` 预烘，绘制退化成 1:1 整数 blit。
   变体(3) × 档位(3) × 翻转(2) = 18 种组合，够打散复制感。
4. **HUD 里所有"每帧重建的渐变/路径"预烘**（v0.5.2）。HUD 是**常驻层**，
   每个探索场景每帧都要画一遍：
   - `G.UI.icon` 把绘制本体抽成模块级 `drawIcon()`，按 `kind|size` 预烘成小画布再 blit
     （`stone` 每次都要现建线性渐变，`qi`/`po` 要现描路径）。颜色全写死，缓存安全。
   - HUD 资源格底、场景铭牌底改走 `G.UI.panel(..., { paper:false, shadow:false })` ——
     它自带缓存，退化成 1 次 blit，不再现描圆角矩形 + 现填 + 现描边。
   - 消融实测（禁用 `_drawHUD` 对比）：开销从 ~0.9—1.1ms/帧降到 **~0.5—0.7ms/帧**。
     > 消融脚本是一次性的，没留在 `tools/`：这台机器噪声比信号大
     > （`field full` 4.72 而同一轮 `field noHUD` 5.48 —— HUD 不可能让它变慢），
     > 要测就多跑几轮取每对的最小值。

#### 量性能必须用对工具

- **逐阶段计时在 Chrome 上不可信**。Canvas2D 是**延迟渲染**的，`drawImage` 只是把命令
  塞进 display list，真正的光栅化发生在 flush 时 —— 给每个 `_draw*` 包一层计时，
  时间会被记到"恰好触发 flush 的那一步"头上。曾把地面层的开销全记到 `_drawDecor`，
  得出完全相反的结论。要看真实开销，用**消融**（`browser-probe.js ablate`：
  把某一步换成空函数，比较真实 rAF 帧间隔的差值）。
- **消融的"基准帧间隔"要先怀疑**。`ablate` 是先把 60 帧同步渲染灌下去、再采样 rAF，
  合成器还压着一堆待画内容，于是 `field / cave / field_temple` 会读到 **33.3ms（30fps）**，
  而同一份代码 `bench-frame.js` 的最小帧耗只有 3.7—4.7ms —— **差 7 倍，是量法不是代码**。
  真正可信的是 `perf` 的「每帧」列（同步平均）。
- **消融结果的解读方式**：如果**每一个**步骤禁用后都得到同一个改善值
  （例如 `field` 里 13 个步骤全是 `-16.6ms`），那说明**没有任何一步是瓶颈**，
  只是整帧刚好越过 vsync 边界（16.7ms）掉到了下一个档（33.3ms）；
  这时候"优化哪一步"是伪命题。只有当**少数几步**显著大于其它步时，才有真瓶颈。
- **软件光栅器与浏览器差好几倍**（`bench-frame.js` 用 @napi-rs/canvas）。
  卡顿是玩家在浏览器里感受到的，最终要在浏览器里量。
- `WIN=1920,1080` 可让探针触发 S=4（1080p 全屏的 worst case，画布比 S=3 大 78%）。
  `GPU=1` 切到 GPU 加速档；默认 `--disable-gpu` 是刻意选的保守档（数值稳定、可跨机比较）。
