# 2. 六大循环闭环追踪（更新 ⑤⑥）

```
①战斗闭环（秒级）  指令→伤害/状态→结算反馈→MP/伤害资源
②养成闭环（世内）  灵气→破境丹+天劫→境界↑→面板↑→打更强敌人
③副本闭环（界内）  抽5副本→推进/刷秘术资源→第5副本→飞升
④轮回闭环（跨世）  战死→仙力结算→五线灌注→重roll→下一世变强
⑤世界闭环（长线）  凡(gl63)→灵(gl90)→仙(gl144)→[三界地狱碎片]→道(gl171)      ← 本版修订
⑥终局闭环（结局）  飞升仙界裁决五结局；道界证道祖→自由道境                      ← 本版修订
```

| 循环 | 投入 | 过程 | 产出 | 再投入/出口 | 闭环 |
|---|---|---|---|---|---|
| ①战斗 | MP、指令 | 行动条/状态/前后排（v2.1） | 灵气、灵石、妖丹、掉落 | 反哺养成/经济 | ✅ |
| ②养成 | 灵气、破境丹 | 天劫/心魔（v2.6）；**野外刷怪供灵气**（C6） | 境界、面板 | 解锁更高副本 | ✅ |
| ③副本 | 寿元、行动 | 九关/五关（副本 Boss v3.3） | 秘术、资源、通关 | 飞升上界 | ✅ |
| ④轮回 | 当世经历 | 仙力结算（v0.4） | 仙力、五线灌注 | 下一世初始变强 | ✅ |
| ⑤世界 | 通关第 5 副本 | **飞升接引（普通即可）** | 世界解锁、**地狱另给称号/永久加成/碎片** | 进入更高世界 | ✅ |
| ⑥终局 | 渡劫 / **三碎片** | 结局裁决 / 道界连战 | 五结局 / 道祖 | 自由道境（终点） | ✅ |

> ⑤ 的**再投入路径现在是双轨**：主线（普通通关 → 飞升）保证推进；支线（地狱通关 → 永久 +10% + 碎片）保证长线目标。
> 两条轨都通，不存在"必须打地狱才能继续"的卡点。

# 4. 本次审计发现并闭合的缺口

> 承接 v3.2 报告的 G1–G10；本版新发现 G11–G18，**带 ✅ 的已在本轮代码中闭合**。

### G11 当前界有两个真相源（✅ 已修）
- 问题：`player.activeWorldId()` 读 `meta.progress.activeWorld`（`ascend` 会写它），
  而 v1.0 又新增了 `save.mainWorld` —— **两个字段会分叉**（飞升后 `activeWorld` 变了、`mainWorld` 没变）。
- 闭合：**删掉 `save.mainWorld`**，当前界只有一个真相源 = `meta.progress.activeWorld`；
  `save.entrances` 改为**按界分桶** `{fan,ling,xian,dao}`，回访下界时原落位仍在。
  迁移：v3 档若 `entrances` 是数组，按 `mainWorld` 归入对应桶后转成对象；`mainWorld` 删除。

### G12 入口可能落在「没有裂隙位」的区域（✅ 已修）
- 问题：`rollEntrances` 从该界**全部**区域抽，会抽到凡界 F1–F3（复用现有手写地图，没有 `special` 位）
  与安全区（市镇）。落位后地图上**什么都不会出现**，且不报错。
- 闭合：候选收紧为**生成型 + 非安全区**（`regions.entranceCandidates`）。

### G31 契约用时间播种的全局 RNG 做概率采样 → 偶发假红（✅ 已修，v0.11.1 · 工具链类）

- 问题：`zone.weights` 断言"中间区双只组出现率约 30%"，采样 400 次却**偶尔报 38.3%**（阈值 30%±8）。
  重跑常常又过 —— **同一份代码时红时绿**。
- 真因：采样用的是**全局 `G.rng`**，而它在 `rng.js` 载入时以 `Date.now()` 播种
  （`new RNG((Date.now() & 0xffffffff) ^ 0x9e3779b9)`）→ **每次运行的随机序列都不同**。
  400 次采样的标准差本身就有 ±2.3pp，叠上阈值边界，约 5% 的运行会误报。
- 闭合：采样前把 `G.rng` 换成固定种子实例（`new G.RNG(20260926)`）、采样数提到 1 200，
  跑完**还原** `G.rng` → 连跑 3 次稳定通过。
- 教训：**概率类断言必须自带确定性随机源，不能蹭全局 `G.rng`**。
  这与 G26（世界种子取自 `Date.now`）是**同一类病**：凡断言里出现"随机"，先问"这个随机的种子是谁给的"。
  → 全项目纪律：`G.rng` 只服务**运行时玩法**；**测试里的采样一律换固定种子 RNG 并在结束后还原**。

### G33 `Btn` 构造器漏拷新字段 → 加了字段却静默不画（✅ 已修 · 接线类）

- 现象：v0.11.4 给储物面板做「方格陈列」时，给 `G.UI.Btn` 加了 `sub` 副行（格子里放
  「名称 + ×数量」两行）。字段加了、渲染分支也写了，**但格子副行就是不出现**，且**不报任何错**。
- 真因：`Btn` 的构造器是**逐字段显式拷贝**（`this.label = o.label;` 一行一个），
  新加的 `sub` / `fs` / `passive` **没进构造器** → `o.sub` 被丢掉，渲染分支永远读到 `undefined`。
- 为什么契约没抓到：`panels.bounds` 验的是"文字是否越界 / 是否压在按钮上"，
  而**根本没画出来的文字不会越界** —— 空断言。
- 闭合：构造器补三个字段；`ui.batch2.contract` 加"储物格子必须带 `sub`"的运行时断言。
- 教训：**"加了字段"和"字段通了"是两件事。** 本项目 `Btn` 走显式拷贝（不是 `Object.assign`），
  所以**每加一个 Btn 字段，必须同步改三处**：构造器拷贝、渲染分支、契约断言。
  这与 G19 / G20 同源（登记了但没接线），但更隐蔽：**G19/G20 是"数据没被消费"，
  G33 是"字段在传递路上掉了"** —— 后者连数据层都查不出来。

### G34 契约的"副作用检查"有**时序盲区**（✅ 已修 · 契约设计类）

- 现象：`ui.batch2.contract` 要钉住「HUD 用的 `xianliLive` 必须是纯函数」（不能写 `meta.achieve`）。
  第一版写法是"调 5 次 → 比对 `meta.achieve` 前后是否一致"。
  反例验证时故意给它加副作用（`xianliLive` 里写 `meta.achieve = {x:1}`），**契约照样全绿**。
- 真因：契约执行到这一条时，**前面的渲染早已调用过 `xianliLive`**，
  `meta.achieve` 在"记 before"之前就已经是脏的了 → `before === after` → 判定通过。
  **副作用检查只在"该函数从未被调用过"时才有效**，而它必然不是。
- 闭合：改成**源码闸 + 运行时哨兵**双轨 ——
  ① 源码闸：正则扫 `player.js` 的 `xianliLive` 函数体，出现 `meta.` / `G.game.` 访问即报；
  ② 运行时哨兵：**先把 `meta.achieve` 摘掉**（`delete`），再调 3 次，
  若它被重新写回来 → 有副作用（记下原值并还原）。
  **"摘掉再看它回不回来"比"前后比对"强**：前者不依赖"函数此前没跑过"，后者依赖。
- 教训：**"前后比对"型断言对"幂等但不纯"的函数无效。**
  凡断言"某函数无副作用"，要么看源码，要么**把它的作用对象摘空再看会不会长回来** ——
  单纯比对快照，等于在函数已经跑过 N 遍之后再问"你刚才改了吗"。

### G35 无头环境的"像素比对"断言恒判相同（✅ 已修 · 工具链类）

- 现象：`ground.type.contract` 要钉住「`cave` 与 `bloodcave` 的地面纹理必须可区分」。
  第一版写法是取两张纹理的 `getImageData` 逐像素比 —— 结果**恒定判为"相同"**，契约报错。
- 真因：**无头 smoke 用的是桩 canvas**，`makeCanvas` 里 `getImageData: () => ({ data: new Uint8ClampedArray(4) })`
  —— **恒返回 4 个零字节，与实际画面无关**。两张图的 `data` 都是 `[0,0,0,0]`，当然"相同"。
  这一条与 `www/assets/README.md` 早已写明的"无头测试跑不到素材路径"是**同一个根因**，
  但表现更隐蔽：**它不报"取不到数据"，而是报一个看起来像真 bug 的结论。**
- 闭合：换成 **源码闸 + 对象同一性** 双轨 ——
  ① 源码闸：`gCave` 与 `gBloodcave` 的函数体（**剥注释后**）逐字不同，且 `gBloodcave`
  必须带 M1 §5.1 规定的基色 `#5a3a3c`；
  ② 运行时：`groundTex('cave', pal) !== groundTex('bloodcave', pal)`（不同缓存条目 = 不同生成器）。
  真·逐像素验证留给 `tools/browser-probe.js`（真 canvas）。
- 教训：**在桩环境里，任何"读回像素"的断言都是假的。**
  桩能验的是"调用路径与登记关系"，验不了"画出来长什么样" ——
  **凡涉及像素结果，一律去 `browser-probe`，不要在 smoke 里造一个恒真的断言。**

### G36 源码闸没剥注释 → 注释里提到符号名就让闸失效（✅ 已修 · 契约设计类）

- 现象：`ground.type.contract` 的 ② 要钉住「`_drawShade` 的提前返回必须走 `_isCaveGround()`」，
  写法是 `sh.indexOf('_isCaveGround()') < 0`。反例验证时把它改回 `kind === 'cave'`，**契约没报**。
- 真因：我在 `_drawShade` **上方**写的说明注释里，正好有一句
  "判据用 `_isCaveGround()` 而不是 `kind === 'cave'`" ——
  注释进了切片，`indexOf` 恒真。**闸检的是"这个符号有没有出现过"，而不是"代码有没有用它"。**
- 闭合：所有源码闸统一**先剥注释再切片**（`stripC`：去掉 `/* */` 与行注释），
  且这条 `stripC` 提升为**源码闸的通用前置**，不再逐条各写。
- 教训：**源码闸的切片里，注释是噪音，而且是"会主动说谎的噪音"** ——
  越是把"为什么这么写"解释清楚的注释，越容易包含被闸的符号名，越容易让闸失效。

  **契约写完必须反例验证 —— 而反例要专门针对"注释/顺序/时序"这类非逻辑路径去试。**

### G37 基线取在"制造前置条件"之前 → 断言恒真（✅ 已修 · 契约设计类）

- 现象：`m1.bloodnight.contract` 验「沈伯燃命（`kind:'ally'`）会重创血面」，写法是

  ```js
  const hpBefore = boss.hp;                      // ← 在压低血量之前取
  boss.hp = Math.round(boss.maxhp * 0.54);       // 制造触发条件
  bx._bossPhase(boss);
  if (!(boss.hp < hpBefore)) errors.push('沈伯燃命应重创血面');
  ```

  反例验证时把 `ph.kind === 'ally'` 改成 `'allyXX'`（**让阶段彻底空转**），**契约没报**。
- 真因：`hpBefore` 取的是**满血**。阶段空转时 `boss.hp` 仍 = `0.54 · maxhp`，
  而 `0.54 · maxhp < maxhp` **恒成立** → 断言恒真。
  **"制造前置条件"这一步本身改了被观测的量，基线必须在它之后取。**
- 闭合：`hpBefore` 移到压低血量**之后**；并把反例固定为"让阶段空转"这一种最狠的改法。
- 教训：**凡是"先摆状态、再断言状态变化"的契约，基线一律取在摆完状态之后。**
  与 G34（前后比对对幂等函数无效）同族：**契约里的"前后"必须真的是同一件事的前后。**

### G38 反例脚本的备份取自"修复前" → 还原把当轮修复一起抹掉（✅ 已修 · 工具链类）

- 现象：`_gen/rev4.sh` 的 `restore()` 从 `_gen/_bak5/` 还原。而 `_bak5` 是**本轮开工时**拷的，
  之后我在本轮里又修了 `_transition` 的 `spawn` 兜底、加强了血夜红雾 ——
  这些**都在备份之后**。跑完反例 `restore()`，**修复被静默还原回缺陷版本**，
  且因为 `_transition` 那条路径只有剧情演出才会走到，**冒烟照样全绿**。
- 真因：把反例备份当成了"当轮代码的快照"，但它在时间上是"当轮开工前的快照"。
- 闭合：**每次在轮内修完 bug，立刻刷新反例备份**（`cp` 覆盖 `_bak*`），
  或在反例批次结束后 `git diff` 复核"修复是否还在"。
- 教训：**反例脚本的还原目标是"当前正确版本"，不是"历史某版本"。**
  判断依据不能是"冒烟过了"，而要看**被改的那几行代码现在长什么样**（`grep` 具体串）。
  这条与 G26/G31（时间源）同类：**先怀疑"我手上这份备份是哪一刻的"，再怀疑业务。**

### G39 反例串与实现不逐字一致 → "改坏"没发生，契约当然不报（✅ 已修 · 验证方法类）

- 现象：v0.12.0 做反例验证时，"把追踪竖标改回 `default` 变体"这条**没命中**，
  一度以为契约漏了这条覆盖。实际是替换串写成了**多行**
  （`variant: 'plain',` 换行再接 `label: '任务追踪',`），`rep.js` 没匹配上 →
  **文件根本没被改** → 契约如实报告"一切正常"。改用单行串后立刻命中。
- 真因：把"契约没报"直接当成"契约有缺口"，**没先确认"改坏"这一步是否真的生效**。
- 闭合：反例串**优先用单行**（单行子串匹配最可靠）；确需多行时先用 `grep -c` 确认唯一命中；
  跑反例时**先看 `rep.js` 的替换计数**，再跑 smoke。
- 教训：**反例验证的前提是"改动确实落地了"。** 一条反例不命中，先分三种可能：
  ① 串没匹配（改坏没发生）；② 契约漏了（真缺口）；③ 断言被别的东西遮蔽（如注释里的同名符号）。
  直接跳去补契约，是**在错误的前提上施工** —— 与 G36（源码闸没剥注释）、
  G38（备份取的是"开工前"而非"修复后"）同属**"验证工具自身的正确性"**问题。

> 同批还有一条**真契约缺口**（已补）：契约在 `_padButtons()` 之后**立刻**数按钮数，

### G40 同一件事写了两条判据 → 其中一条恒真，变成假红（✅ 已修 · 契约设计类）

- 现象：`about.layout.contract` 里我同时写了「正文末行底不得越过关闭按钮顶」与
  「单条文案宽度不得远超内宽」两条判据。第二条对**本来就该折 2 行**的文案恒成立，
  于是契约刚写完就报了一条假红。
- 真因：把"我觉得应该管"的两件事都写成断言，而它们其实是**同一件事的不同侧面**
  （文案宽 → 折行数 → 末行位置）。只要折行预算那条对，宽度那条就是冗余的噪声。
- 闭合：删掉冗余判据，只留"末行底 ≤ 按钮顶"。判据数越少，假红的来源越少。
- 教训：**一个不变量只留一条判据。** 两条判据描述同一件事时，
  较松的那条恒真、较紧的那条才是契约 —— 而较松的那条会在别人改数值时先报，
  把注意力引到错的方向（同 G24「文字压按钮 ≠ 越界」、G30「只查左端」同族：
  **契约的判据边界要刚好卡在"会出问题"的那一侧**）。

### G41 `G.VERSION` 停在占位值从未随版本升级（✅ 已修 · 静默类）

### G42 反例判据的 grep 太窄 → 漏掉"加载崩溃"型失败（✅ 已修 · 验证方法类）

- 现象：反例脚本用 `node tools/smoke.js | grep -E "✗"` 判断"契约有没有报"。
  把 `MIST_C` 改名、把 `isMist` 删掉这类**会让脚本加载失败**的改动，smoke 打印的是
  ` - 加载失败 js/core/ui.js: MIST_C is not defined`（走"发现问题"清单，前缀是 ` - `），
  **一条 `✗` 都没有** → 反例脚本判定"未命中"，于是我们转头去补契约，其实契约早就生效了。
- 真因：失败有三种输出形态 ——
  ① 契约内部 `errors.push` + 自打印 `  ✗ ...`；② 契约抛异常 → 外层 catch 打印 ` - [契约名] ...`；
  ③ **脚本加载失败** → ` - 加载失败 <文件>: <原因>` + 后续契约全部雪崩（`Cannot read properties of undefined`）。
  只 grep 第一种，就会把后两种当成"契约没生效"。
- 闭合：反例脚本的判据改成 `grep -E "✗|发现问题|^ - "`（三种形态全收）。
- 教训：**反例验证的判据本身也要验** —— 判据窄了，比没有反例更危险：
  它会让你以为"契约覆盖到了"，从而停止追查。
  与 G39（反例串没匹配 → 改坏没发生）是**同一条纪律的两个面**：
  **一条反例"没命中"，先怀疑验证链路，再怀疑契约。**
  排查顺序：① 替换串真的改到了吗（`grep` 改后的文本）→ ② smoke 的输出被判据吃了吗
  （先看完整输出，再看过滤后的）→ ③ 才轮到"契约真缺口"。

### G43 判据只查符号名 → 同一符号在源码多处出现时恒真（✅ 已修 · 契约设计类）

- 现象：契约用 `ui.indexOf('opt.tex') < 0` 判断"面板纹理开关是否改名到位"。
  反例把 `if (opt.tex === undefined) opt.tex = true;` 改回 `opt.paper` 后，**契约不报** ——
  因为 `opt.tex` 在**缓存键**里也出现（`(opt.tex ? 1 : 0)`），`indexOf` 照样命中。
  后果是"纹理永远不画"（`opt.tex` 恒 `undefined`）这种半改**静默通过**。
- 闭合：判据从"符号存在"改成**匹配整句默认赋值** `/if \(opt\.tex === undefined\) opt\.tex = true;/`。
- 教训：**源码闸的粒度要匹配"改动的粒度"，不是匹配"符号的粒度"。**
  同一符号在一份文件里出现 N 处时，`indexOf(符号) >= 0` 只能证明"文件里提到过它"，
  证明不了"该接的地方接上了"。
  与 G36（闸没剥注释）同族 —— 都是**闸的判据比它要守的不变量松**。
  写闸时的自检问题：**"把这一行改坏，闸还会绿吗？"**

### G26 轮回回归基线不可复现（✅ 已修，v0.9.0 · 工具链类）

- 问题：`rebirth.js` 的「第 2 世变强」那行**偶尔**从 `攻击 41→43` 变成 `41→46`，
  其余数字（仙力 +386）完全不变。实测 30 次：**28 次 43、2 次 46**。
- 误判：旧版 HANDOVER 归因于"新增随机消耗推移了全局 `G.rng` 序列" —— **方向错了**，
  于是每次改代码都去数"有没有多调一次随机"，既查不出也防不住。
- 真因：`reincarnation.js` 的非锚世世界种子取自 `Date.now()`
  （`var seed = anchor ? 20260924 : (Date.now() & 0x7fffffff);`）。
  `rebirth.js` 的灵根/天赋早已用 `rollFixed()` 钉死、天赋清空，第 1 世（锚世）完全确定 ——
  **唯一的时间输入就是这一句**。
- 闭合：`rebirth.js` 在**脚本载入之后**把 `Date.now` 钉成常量
  （`G.rng` 的种子在 `rng.js` 载入时已取过真实时间，不回改，故第 1 世行为完全不变），
  第 2 世种子随之固定 → 连跑 6 次恒为 `41→43`。
- 教训：**一个不可复现的基线等于没有基线。** 凡"偶尔不一样"的回归数字，
  先找**时间源**（`Date.now` / `performance.now` / `Math.random`），不要先假设是业务逻辑的随机消耗；
  用跑 N 次统计分布代替盯一次输出。详见 `HANDOVER.md` §5.9。
